# CLAUDE.md – IPVIO Stream for webOS

Working rules for AI-assisted changes to this repository. Read this file first in every session, then `GLOSSARY.md`, `docs/PLAN.md` and `docs/tasks/WORK_STATE.md`. Use the glossary's terms in code, issues and docs. Decisions with lasting impact are ADRs in `docs/adr/`; flag anything that contradicts one.

## 1. Project

- **IPVIO Stream for webOS** is a port of the IPVIO Stream Android TV IPTV player to LG webOS TVs. GPL-3.0, like the original.
- **Reference:** Android IPVIO Stream **1.4.8**, commit `f4a0360` (`D:\Projects\IPVIO Stream`, GitHub `MusaAliji/IPVIO-Stream`). "Same as Android" always means this commit until a parity sync task moves it (T-083).
- **Goal:** the same screens, layout, navigation, remote keys, strings and features as Android. Anything the platform cannot do is listed in `docs/PARITY.md` with a reason. Never drop a feature silently.
- **Stack:** TypeScript, Preact, Norigin spatial navigation, Vite with the legacy plugin, Vitest, `ares-cli` packaging. A webOS JS service (Node on the TV) ships in the same `.ipk`.
- **IDs:** app `com.ipvio.stream.webos`, service `com.ipvio.stream.webos.service`. Never change them after the first release (user data is bound to the app id).
- **Minimum webOS:** 4.0 (Chromium 53). Main test device: LG 55UR80003LJ, webOS 23, registered in `ares-setup-device` as `lgtv`. Emulators for webOS 4 and 6 for smoke tests.

## 2. Principles

1. Port, do not redesign. When unsure how something looks or behaves, read the Android code.
2. Protect data compatibility with Android: preference names and keys, backup JSON, item ids (Java `String.hashCode()`), Drive file format.
3. Logic lives in pure TypeScript modules (no DOM, no webOS APIs) so Vitest can cover it. Platform access goes through adapters (`platform/`), never directly from screens.
4. Do not invent dependencies. Adding, removing or upgrading a dependency needs the maintainer's approval (section 6).
5. One task, one problem, one branch, one PR.

## 3. Environment

- The assistant can run Node, npm, Vitest, lint and `ares-*` commands, and can install to the TV only when the maintainer asks (the TV may be off).
- Never report a device test as passed unless it was run on the device. State which checks ran and which did not.
- Every PR ends with concrete test steps for the 55UR80.

## 4. Language

- Everything in the repository is English: code, comments, file names, commit messages, PR and issue text, docs.
- UI strings come from the Android dictionaries (`src/i18n/*.json`, generated by `scripts/dict-to-json` from the Android `Dict*.kt` files). The German text is the key, as on Android (Android ADR 0002). **Never hand-edit the generated JSON.** New strings are added on Android first, or listed in the PR for the maintainer.
- When docs refer to a UI label, quote the English label, never the German key.

## 5. Protected areas (no change without an approved plan)

- Preference file names and keys mirrored from Android (`ipvio_*`, profile suffix `_p<ID>`).
- Backup JSON format and the list of backed-up names (mirrors Android `Backup.kt`).
- Item id computation (Java `String.hashCode()` port).
- Phone remote routes and parameters (`/r`, `/b/CODE`) and the port range 8765–8775.
- App id, service id.
- Player engine selection (decided by the playback spike, T-012).

## 6. Approval required before implementation

- Storage format changes, anything with a risk to user data.
- Dependency changes, build or CI changes, new workflows.
- Removing or degrading any feature, or adding an entry to `docs/PARITY.md`.
- Changes to secrets handling, authentication, the phone remote or the JS service's network exposure.

## 7. Tasks and workflow

- Tasks live in `docs/tasks/T-xxx-*.md` and as GitHub issues (`T-00N` is issue `#N`). The task file holds the scope; the issue tracks status through the triage labels (`ready-for-agent`, `ready-for-human`, `needs-triage`).
- Blockers are native GitHub "blocked by" links. The next task is the frontier: an open `ready-for-agent` issue whose blockers are all closed, lowest number first.
- Work only on the assigned task.
- `ANALYZE → PLAN → APPROVAL → IMPLEMENT → VALIDATE → DOCUMENT → REPORT`
  - **Analyze:** read the Android files listed in the task, and the tests to port.
  - **Plan:** list files to add or change and why. Large tasks wait for approval.
  - **Implement:** port the Android tests first where they exist; they are the reference for correct behaviour.
  - **Validate:** lint, Vitest, `.ipk` build; list device test steps.
  - **Document:** task file status and test results, `CHANGELOG.md`, `docs/PARITY.md` if behaviour differs.
  - **Report:** what changed, checks run, what is open, risks.

## 8. Session handoff

Before ending a session, update `docs/tasks/WORK_STATE.md`: current task, done steps, changed files, test results, open problems, next step.

## 9. Security rules

- No API keys, OAuth client ids or secrets in the repository or logs. Fallback keys come from CI secrets at build time (T-057).
- Validate input from playlists, phone remote requests and backups.
- The JS service never listens on the network except the phone remote server, which needs the 4-digit code.
- Known limits copied from Android: phone remote uses plain HTTP on the LAN; secrets fall back to plaintext without `crypto.subtle`.

## 10. Branches and releases

- `main`: releases only, changed only by a merge commit from `dev` via a PR.
- `dev`: development. Branches `feat/T-xxx-*`, `fix/T-xxx-*`, `docs/T-xxx-*` start from `dev`; PRs go into `dev`.
- Versioning: 0.x until parity, 1.0.0 at the end of M12. About shows "based on Android 1.4.8".
- A push to `main` publishes `v<version>` with the `.ipk` and the Homebrew Channel manifest (from T-049). The assistant does not publish releases; the maintainer merges.
- No force pushes to `main` or `dev`.

## 11. Subagents

Use subagents only for large, read-only questions with a precise brief (for example "list every place in the Android code that reads `ipvio_sportfavs`"). The main agent owns integration. No parallel edits to the same file.
